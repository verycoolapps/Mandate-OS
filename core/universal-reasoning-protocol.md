# MANDATE 360° Professional Analysis Protocol

## The Universal Reasoning Framework

Every professional role in MANDATE OS follows this protocol when analyzing significant problems. This is not a checklist — it is a reasoning architecture.

---

## DIMENSION 1 — SITUATION UNDERSTANDING

### Purpose
Establish ground truth before any analysis begins.

### Investigation Questions
- **What exactly is happening?** — Precise problem statement
- **What is the actual problem?** — Core issue vs. symptoms
- **What is merely a symptom?** — Surface-level manifestations
- **What is the expected condition?** — Desired state
- **What is the current condition?** — Actual state
- **What evidence supports the observation?** — Data, metrics, observations
- **What assumptions are being made?** — Explicit and implicit
- **What information is missing?** — Gaps that affect analysis

### Methodology
- Gather quantitative data where available
- Collect qualitative observations
- Document all assumptions explicitly
- Identify information gaps
- Establish baseline understanding

### Output
- Situation description
- Problem statement
- Evidence inventory
- Assumption log
- Information gap list

---

## DIMENSION 2 — WHY ANALYSIS

### Purpose
Investigate root causes, not just surface explanations.

### Investigation Questions
- **Why did this happen?** — Direct causes
- **Why does this matter?** — Significance and impact
- **Why has the problem persisted?** — Historical patterns
- **What are the underlying causes?** — Deep causal factors
- **What organizational or environmental factors contributed?** — Context
- **What incentives or behaviors created the situation?** — Motivations
- **What structural weaknesses exist?** — Systemic issues
- **What evidence could disprove the current explanation?** — Falsification

### Methodologies
Select appropriate methodologies based on problem type:

#### Five Whys
- Ask "why" five times to drill down to root cause
- Effective for straightforward causal chains
- Risk: Can lead to single-cause oversimplification

#### Fishbone Analysis (Ishikawa)
- Categorize causes: People, Process, Equipment, Materials, Environment, Management
- Effective for complex, multi-factor problems
- Visual mapping of causal relationships

#### Root Cause Analysis (RCA)
- Systematic investigation using change analysis, barrier analysis
- Effective for incidents and failures
- Focuses on what changed and why barriers failed

#### Fault Tree Analysis
- Top-down deductive analysis
- Maps all possible causes of a failure
- Effective for technical and safety-critical systems

#### Causal Loop Diagrams
- Maps feedback loops and system dynamics
- Effective for complex, systemic problems
- Identifies reinforcing and balancing loops

#### Pareto Analysis
- 80/20 rule application
- Identifies vital few causes vs. trivial many
- Effective for prioritization

#### Systems Thinking
- Examines interconnections and patterns
- Identifies leverage points
- Effective for organizational and strategic problems

### Output
- Root cause identification
- Causal chain documentation
- Supporting evidence
- Confidence assessment
- Alternative causal explanations

## DIMENSION 3 — HOW ANALYSIS

### Purpose
Understand system mechanics and implementation requirements.

### Investigation Questions
- **How does the problem operate?** — Mechanism of action
- **How did the situation develop?** — Evolution over time
- **How can it be resolved?** — Solution mechanisms
- **How should the proposed solution work?** — Solution architecture
- **What dependencies exist?** — Prerequisites and constraints
- **What implementation sequence is required?** — Ordering and phasing
- **What resources are necessary?** — People, capital, technology, time
- **What could prevent implementation?** — Barriers and risks

### Methodology
- Map system components and interactions
- Identify process flows and handoffs
- Document dependencies and constraints
- Sequence implementation steps
- Resource requirement analysis
- Barrier identification

### Output
- System mechanics description
- Implementation sequence
- Resource requirements
- Dependency map
- Barrier analysis

### Mandatory Analysis

- Cost reductions
- Efficiency improvements
- Quality enhancements
- Competitive advantages
- Customer satisfaction
- Strategic positioning
- Risk reduction
- Capability expansion
- Future flexibility

#### What We Sacrifice
- Financial investment
- Time commitment
- Human resources
- Operational complexity
- Existing capabilities
- Short-term profitability
- Organizational capacity
- Flexibility constraints
- Speed trade-offs

#### What We Risk

- Operational disruption
- Reputation damage

- Technical failure
- Regulatory complications

## DIMENSION 6 — ALTERNATIVE SCENARIOS

### Purpose
Generate materially different approaches for comparison.

### Scenario Types

#### 1. Conservative Approach
- Minimal change
- Low risk
- Proven methods
- Slower implementation
- Lower upside
- Higher certainty

#### 2. Balanced Approach
- Moderate change
- Managed risk
- Hybrid methods
- Reasonable timeline
- Balanced upside
- Moderate certainty

#### 3. Aggressive Approach
- Significant change
- Higher risk
- Innovative methods
- Faster implementation
- Higher upside
- Lower certainty

### For Each Scenario
- **Expected outcome** — What success looks like
- **Required investment** — Financial, human, time
- **Implementation difficulty** — Complexity, dependencies
- **Risk exposure** — What could go wrong
- **Time to value** — When benefits materialize
- **Long-term consequences** — Future implications
- **Reversibility** — Can we undo this if needed?

### Output
- Scenario descriptions
- Comparative analysis
- Risk-return profiles
- Implementation feasibility
- Recommendation rationale

## DIMENSION 7 — DECISION RECOMMENDATION

### Purpose
Deliver clear, evidence-based guidance.

### Components

#### Recommended Decision
- Specific recommendation
- Action or inaction
- Phasing if applicable

#### Why This Decision Is Preferable
- Primary rationale
- Key supporting factors
- Evidence linkage

#### Evidence Supporting Recommendation
- Data references
- Analysis results
- Stakeholder input
- External benchmarks

#### Alternatives Rejected
- What was considered
- Why it was rejected
- Under what conditions it would be viable

#### Conditions Under Which Recommendation Would Change
- What new information would change the decision
- What contextual shifts would invalidate the recommendation
- What threshold crossings would trigger re-evaluation

#### Confidence Level
- **High:** Strong, relevant, corroborated evidence; low material uncertainty.
- **Moderate:** Useful evidence with stated limitations or meaningful uncertainty.
- **Low:** Weak, indirect, or context-mismatched evidence; significant uncertainty.
- **Insufficient evidence:** No adequate basis to assess or conclude.

Use these as qualitative evidence-based labels, not percentage bands. Explain the supporting evidence and uncertainty; do not imply numerical precision without a relevant, calibrated method.

#### Remaining Uncertainties
- What is still unknown
- What assumptions are critical
- What risks are unquantified

### Output
- Decision statement
- Rationale summary
- Evidence summary
- Confidence assessment
- Uncertainty inventory
- Change triggers

## Protocol Application Guidelines

### When to Apply Full Protocol
- Strategic decisions with significant impact
- Major investments or commitments
- Organizational changes
- Product or service launches
- Risk-critical decisions
- High-stakes situations

### When to Apply Simplified Protocol
- Routine operational decisions
- Low-risk, low-impact choices
- Time-critical situations requiring rapid response
- Well-understood problems with established solutions

### Protocol Adaptation
- Adjust depth based on problem complexity
- Focus on most relevant dimensions for the specific context
- Combine dimensions when appropriate
- Iterate through dimensions as new information emerges

### Anti-Patterns to Avoid
- **Skipping dimensions** — Do not omit analysis steps without justification
- **Mechanical application** — Adapt the protocol to the problem, don't force the problem into the protocol
- **Pretending certainty** — Use confidence levels honestly
- **Ignoring trade-offs** — Every decision has costs; make them explicit
- **Fabricating data** — State assumptions, don't invent facts

## Protocol Integration with Role Intelligence

Each role applies the protocol through its specialized lens:

- **CFO** applies financial analysis depth to trade-offs and impact
- **CTO** applies technical rigor to how analysis and implementation
- **Product Manager** applies customer lens to impact and success measurement
- **HR Director** applies organizational lens to long-term intelligence
- **Legal Counsel** applies regulatory lens to risk and consequences

The protocol provides the structure; the role provides the specialized reasoning.
